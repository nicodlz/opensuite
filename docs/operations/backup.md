# Backup and recovery on one VPS

This is a **downtime** backup. At 01:00 UTC the systemd timer invokes the
Compose helper services. The controller stops running Caddy, API, Drive and
Stalwart containers; takes `pg_dump` custom-format snapshots of both databases,
`pg_dumpall --globals-only`, the complete stopped Stalwart RocksDB directory
(including WAL), the Compose secrets and Caddy volumes, configuration and both S3 object
prefixes; checks the object copies byte-for-byte; and starts the previously
running services again. The staged set is then encrypted and uploaded by
restic 0.19.1. A snapshot is published only if every capture succeeded; pruning
runs only after a successful snapshot. PostgreSQL dumps are individually
consistent; the stopped application writers make them a coordinated set.

[Stalwart's backup procedure](https://stalw.art/docs/management/maintenance/backup/)
explicitly permits stopping the server and copying the complete RocksDB
directory. It requires the data store to be copied before the blob store and
no intervening blob purge. Stopping Stalwart ensures this. Unlike an atomic
filesystem snapshot, a file-by-file copy while Stalwart is running is unsafe.
This solution favors portability over availability: copying and checking large
object prefixes can make downtime long. Size the encrypted scratch filesystem
for the entire uncompressed set plus dumps, and monitor its free space. The
scratch files are removed on normal exit or handled termination; inspect and
securely clean stale directories after a crash or power loss.

**Scope and prerequisites:** This captures current object bytes, not old
versions, bucket policies, incomplete S3 multipart uploads, or arbitrary S3
metadata. Drive's database holds its content type; pending uploads must be
retried. It assumes the keys generated by OpenSuite/Stalwart are representable
as local file paths and are not modified by any other principal during the
copy. Use separate buckets or non-overlapping prefixes for mail and Drive.
Before enabling the schedule, stop any independently deployed ingestion worker,
cron jobs, external database writers, active presigned upload clients, and
other S3 writers/deleters during every capture, including cleanup/lifecycle
jobs. The controller cannot stop external writers. Arrange an operational
maintenance window that enforces this, and do not run migrations, setup jobs,
or `docker compose up` concurrently. Object lifecycle rules must not remove
needed objects during capture. The current Compose file does not run the
planned ingestion worker. An independent inbound archive and replay are
separate recovery requirements, not supplied by this backup.

## Provision and schedule

1. On an encrypted host filesystem install the checkout at `/opt/opensuite`,
   configure `.env` and all service secrets as for production, and create a
   private **separate** B2 bucket/prefix and application key, distinct from
   mail and Drive credentials. The key must allow listing, reading, writing and
   deleting the backup prefix (restic retention needs delete). Configure the B2
   S3 endpoint, not its native API. Check prefix restrictions and TLS with the
   provider. No real B2 behavior has been verified by this project.
2. Copy `deploy/backup/backup.conf.example` to `/etc/opensuite/backup.conf`,
   mode 0600, and fill in its shell assignments. Choose an encrypted,
   access-restricted `BACKUP_SCRATCH` filesystem. Put a strong randomly
   generated restic password in the named file, mode 0600. Protect and test an
   **independent offline copy** of the password, backup key, repository URL,
   Git revision and this procedure: none can be recovered from the repository
   without the password. The backup contains `.env`, the mail secret, generated
   Compose secrets and backup configuration, all encrypted by restic before
   uploading. Docker administrators can read these values; restrict host and
   Docker access. Environment and configuration files must be trusted POSIX
   shell assignments, not arbitrary shell code.
3. Run `deploy/backup/init.sh` once for a new empty repository; it never
   initializes automatically when a backup cannot reach an existing repository.
   Run `deploy/backup/backup.sh` and confirm the JSON `success` event. Review
   the repository and exercise a restore. The script exits non-zero on capture,
   upload, retention or service-restart errors and emits `failure`; `overlap`
   indicates a second run was refused. Helper tools also write diagnostics to
   stderr. Alert on failed systemd units, failure/overlap/restart_failed events,
   missing success events and the age of the most recent successful snapshot.
   A successful capture followed by a pruning failure is reported as failure.
4. Install `deploy/backup/opensuite-backup.service` and
   `deploy/backup/opensuite-backup.timer` into `/etc/systemd/system/` (edit
   paths if the checkout is elsewhere), then run `systemctl daemon-reload` and
   `systemctl enable --now opensuite-backup.timer`. The persistent timer catches
   missed runs after reboot. Check `systemctl list-timers` and the journal.

Restic keeps 7 daily, 5 weekly and 12 monthly snapshots, grouped by captured
path, then prunes unreferenced data. This is a rolling selection, not a
promise of 7+5+12 distinct snapshots. Limit backup-key access, protect the
repository from malicious deletion with an independently managed copy or
compatible immutable policy, and rehearse retention and recovery. B2 object
versioning/lifecycle may retain hidden restic pack versions and incur charges;
policies must not interfere with restic's repository operations.

## Rebuild a new VPS

1. Fence the old host and all external writers. Install Docker/Compose, Git,
   `flock` and the recorded OpenSuite revision at `/opt/opensuite`. Build the
   application images and frontend for that revision as described by the
   installation instructions. Use the same architecture and pinned images.
   Provision an encrypted scratch filesystem and private, **empty** mail and
   Drive buckets/prefixes. For the restored configuration, they must have the
   same endpoints, bucket names and prefixes as the saved `.env` and Stalwart
   registry; use isolated accounts/DNS/networking if testing. If the original
   bucket still contains data, first preserve it independently and arrange an
   empty isolated endpoint with the same bucket names; this script will not
   overwrite it. Reusing an emptied original prefix requires an explicit
   operator decision after independent copies are verified. Configure the
   source access credentials before restoring. Never point recovery at a live
   bucket or run the old VPS simultaneously.
2. Restore the independently held backup configuration, credentials and restic
   password to `/etc/opensuite`, with restricted permissions. In a clean
   checkout with **no `.env` and empty Compose volumes**, run
   `deploy/backup/restore.sh` (or pass a restic snapshot ID). It refuses
   nonempty secrets, Caddy, RocksDB, PostgreSQL volumes or object prefixes. The script
   decrypts to scratch, restores the recorded `.env`, mail secret, Compose and
   Stalwart config, object bytes, secrets and RocksDB volumes, then starts only
   PostgreSQL and restores the roles and both databases. A failed restore may
   leave partial files, volumes or objects: discard the isolated target and
   retry from empty storage. The restored backup configuration is available in
   the encrypted snapshot; retain the independently supplied recovery copy
   until its paths and credentials have been checked.
3. Inspect `.env`, permissions, restored image pins and external secrets;
   ensure the exact Git revision matches `config/git-revision` in the snapshot.
   Confirm the provider credentials and endpoints are correct. Run
   `docker compose up -d`, inspect health, and sign in to an account. Verify a
   known message and attachment, mailbox, calendar, Drive file and both app
   databases. Test search, SMTP and outgoing queue behavior in isolation;
   restored queue entries may be delivered again. Reconcile the inbound
   archive and ingestion ledger before replay or cutover. Only then enable
   external traffic, scheduled workers, backups and DNS on the new host.
   Record timings and results; repeat regularly.

## Recovery objectives and limits

The target schedule is daily, so the nominal RPO is up to 24 hours plus
capture time; failures, downtime, missed monitoring or unrecoverable keys make
it longer. All changes since the last successful coordinated capture can be
lost. A provider's object versioning may retain old object bytes after
replacement or deletion, but does not restore RocksDB, PostgreSQL, secrets,
mailbox indexes, exact object-to-database mappings or data never uploaded.
It is not an application-consistent backup. An independent inbound archive
may allow later mail replay only after reconciliation is implemented and
proved. Database WAL/PITR and continuous backups are not implemented.

RTO is **not yet established**: provision and configure a replacement VPS,
download and decrypt the full snapshot, restore both databases and all
objects, validate and cut over. Transfer throughput, dataset size, DNS,
provider availability and human response dominate. Measure this with a
representative recovery drill before making an operational commitment. The
local disposable integration test is not a measurement of production RTO or
proof of B2 compatibility.

Run the isolated test with `./scripts/backup-integration.sh`; it creates a
throwaway MinIO service and Compose projects, imports mail, captures, destroys
and restores fresh volumes and object prefixes. It makes no AWS or B2 calls.
