# Outbound mail through SES

Stalwart owns the persistent outbound queue and sends non-local recipients through the configured SMTP relay. Local domains retain local delivery. A successful JMAP submission means the message was queued; SMTP acceptance by SES is also not proof of recipient delivery. Configure SES event publishing and monitor bounces, complaints, delivery failures, queue age and expiry separately. The management integration is server-side only. No real SES connection has been tested by this repository.

## Prepare SES and credentials

1. In **eu-north-1**, verify the sender identity and request production access if needed. The current sending rights cover only the verified identity; do not assume other identities are authorized. In the SES sandbox, recipients must also be verified (or use the mailbox simulator), and default quotas are 200 messages per 24 hours and 1 message per second. Check the actual account quotas in SES; request increases before using higher throughput. SES counts recipients against quotas.
2. Generate SMTP credentials for the same region in SES. These are distinct from ordinary AWS API credentials. Store the SMTP password in a restricted file outside the repository and `.env`. The SMTP username is not the password. SES documents [STARTTLS on port 2587](https://docs.aws.amazon.com/ses/latest/dg/smtp-connect.html); the configured endpoint is `email-smtp.eu-north-1.amazonaws.com:2587`, with mandatory STARTTLS and certificate validation. Do not use the adapter's insecure test mode for SES.
3. Put the file path in the shell environment as `MAIL_RELAY_SECRET_FILE` when starting Compose; it is mounted read-only as `/run/opensuite/smtp-secret` in Stalwart. The file and parent directories must be readable/traversable by Stalwart's UID 2000. The server reads the file as a secret reference; the password is not sent in the management API. Back up and rotate it securely. Recreate Stalwart after replacing the bind-mounted file or changing its path; reload and verify delivery after rotation. Do not put the value in logs, environment files or Git.

## Apply

The repository includes `scripts/outbound.mjs` to reconcile the SES relay, but its current management access does not match normal Compose startup: the script authenticates as the recovery `admin`, the loopback overlay only publishes the listener, and normal Stalwart neither activates nor mounts the recovery administrator credential. The separate management account is IP-restricted to the management network and the script does not select that username. The former instruction to read `/run/opensuite/stalwart-admin/password` from the normal Stalwart container cannot work. **Do not leave a recovery override running or expose management access to work around this.** See the [production runbook](../deployment/production.md) being prepared in parallel for the corrected procedure.

The intended relay uses `email-smtp.eu-north-1.amazonaws.com:2587` with mandatory STARTTLS and certificate validation. After applying any corrected procedure, verify the active settings and a controlled message, and remove temporary management access. Settings changes are not transactional; serialize management changes and reconcile ambiguous failures before retrying. Do not delete named route objects while the strategy refers to them: [Stalwart falls back to MX](https://stalw.art/docs/mta/outbound/strategy/) for missing routes. Alert on `smtp.id-not-found` and configuration errors.

The configured remote queue has one delivery thread, retries after 5 minutes, 30 minutes and then 2 hours, a delay notification after 4 hours and expiry after 24 hours. One thread limits concurrency, **not** messages per second or daily volume: enforce SES account rate and rolling quotas upstream, including all senders and other services. Monitor the queue and delivery failures; notifications can themselves fail. See [Stalwart scheduling](https://stalw.art/docs/mta/outbound/scheduling/) and [queue management](https://stalw.art/docs/mta/outbound/queue/).

## DKIM and DNS

The server-side `StalwartAdmin.dkimRecords(domainId)` returns typed TXT records for active keys, and the domain workflow displays records when its provider is configured. The `scripts/outbound.mjs dns` action has the same management-access limitation described above; see the [domain guide](domains.md) and production runbook for the supported workflow.

Publish the returned names and values at your DNS provider, verify propagation and test signatures before sending. No DNS changes are made by this service. Protect Stalwart's data and keys in backups. Review records during key rotation, and retain old records while messages signed with those keys remain in transit. Stalwart signing and SES identity verification/signing are separate; verify alignment for the actual From domain and publish the SES-provided identity records as required. Set SPF and DMARC according to the domain's actual senders and SES configuration. The adapter reports an error if no active supported key exists; it does not verify domain ownership or DNS propagation.

## Rollback and recovery

Pause new submissions, inspect and preserve the queue, and decide how queued mail should be handled before changing routes. The script's `reset` action is subject to the same management-access limitation. When a corrected procedure is available, restoring Stalwart's default local/MX route, scheduling and TLS expressions allows direct MX delivery for non-local recipients and restores Stalwart's default opportunistic TLS behavior; use only when direct delivery is intended and possible. Existing queued recipients may be affected. The named relay objects and secret file are not deleted. Verify the new policy and queue, then remove the secret mount and rotate/revoke credentials when appropriate. For a fail-closed rollback, stop outbound processing instead of selecting direct delivery. Back up the data store and secret separately.
