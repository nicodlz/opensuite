# ADR 0002: Single-server production target

- Date: 2026-10-29
- Status: Accepted target, subject to the implementation and proof gates below; not deployed.
- Scope: A small self-hosted installation. Other providers and an optional HA architecture remain possible.

## Decision and current state

Run a replaceable VPS with the Compose stack, including the frontend and backend, reverse proxy, Stalwart and local databases. Stalwart v1.0.1 uses local RocksDB for structured mail data; PostgreSQL holds application data and a separate Drive database. Mail contents, Drive files and encrypted backups belong in private Backblaze B2 S3-compatible object storage, with separate buckets or prefixes and separate least-privilege credentials for each purpose. The S3-compatible Stalwart blob backend is documented, but its compatibility with B2 on the pinned image is **unverified**; OM-B2-MAIL must prove read, write, deletion, recovery and failure behavior before use. The inbound S3 buffer is separate from permanent mail storage. See [Stalwart evidence](../architecture/stalwart.md).

Today the repository contains a local Compose stack and API skeleton; the database package and web shell are being integrated. The existing Compose file does not yet run the frontend, Drive or ingestion worker. Authentication, the production adapters, backups and the target topology are planned. Nothing is deployed as part of this decision. A development substitute does not prove provider behavior.

Use Amazon SES in **eu-north-1** for sending and receiving. AWS's [General Reference SES endpoints](https://docs.aws.amazon.com/general/latest/gr/ses.html), accessed 2026-10-29, lists the receiving endpoint `inbound-smtp.eu-north-1.amazonaws.com`. For outbound mail, Stalwart relays through SES SMTP with authenticated, certificate-verified **STARTTLS on port 2587**; hosts may filter ports 25 or 587, so test reachability on the selected host. AWS documents 2587 as a STARTTLS port in [Connecting to an SES SMTP endpoint](https://docs.aws.amazon.com/ses/latest/dg/smtp-connect.html), accessed 2026-10-29. Stalwart queues and retries; relay acceptance is not final delivery. Handle bounces and complaints. Each dynamically added domain needs verified ownership, an SES identity in the sending region, and application authorization for its senders before enabling it. AWS describes inheritance and its limits in [SES identities](https://docs.aws.amazon.com/ses/latest/dg/creating-identities.html), accessed 2026-10-29. Support other relays and direct SMTP as separately validated alternatives.

## Inbound preservation and import

The planned path is **SES → temporary Amazon S3 buffer → SNS → SQS with a DLQ → ingestion worker → Stalwart → permanent B2 mail storage**. SES's S3 action emits its SNS notification; it is not an S3 event. The worker imports the original MIME into every resolved mailbox using envelope recipients, including Bcc. An accepted SMTP transaction does not establish that any later step succeeded. [Ingestion](../architecture/ingestion.md) specifies notification fields, size limits, handling and the proof gate; [ADR 0001](0001-architecture.md) distinguishes acceptance, preservation, mailbox availability and sending.

Preserve **both the original MIME and the complete rule-matched envelope recipients** independently of the VPS, together with verdicts and identifiers needed for replay. MIME headers may omit Bcc. SQS and its DLQ are not archives: [AWS documents](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-configure-queue-parameters.html), accessed 2026-10-29, a maximum 14-day queue retention period. Plan a separate managed archival consumer of the SNS notification, independent of the VPS (for example an SNS-triggered Lambda), that writes encrypted metadata durably to private object storage; retain the original S3 object until all intended mailbox imports are confirmed **and** independent archival and the recovery retention policy permit deletion. Preserve a recoverable MIME copy and its metadata beyond import where necessary to replay changes newer than the last database backup. The archive, retries, permissions, retention, encryption keys and relationship to the message object are implementation gates, not existing guarantees. Reconcile source objects and archived notifications; alert and retain or quarantine an orphan object when its routing evidence is unavailable. Test notification-delivery failures and long VPS outages: if the independent archive cannot reliably capture and recover envelope data, this path does not meet the preservation requirement.

Persist per-destination state and an idempotency key; retry safely, reconcile uncertain import outcomes before replay, and alert on backlog age, expired or missing metadata, missing objects, archive failure, import failures and DLQ messages. A unique ledger cannot alone make a remote JMAP import exactly once. Provide audited replay and test crashes at each boundary. OM-INGEST and OM-AWS-IAC must prove the path, including a real-provider test when authorized; if the proof fails, document the blocker and validate direct SMTP as the alternative before cutover.

## Backup and restore

Take at least daily encrypted, consistent backups of RocksDB, both PostgreSQL databases, configuration and the secrets/keys required to restore them to private B2 storage. Protect backup encryption keys separately and test their recovery. Snapshots must cover the ingestion ledger and configuration stored inside RocksDB, not merely the bootstrap file. Coordinate database snapshots with mail blobs, Drive objects and the preserved inbound archive: use versioning or equivalent retention and a checkpoint/manifest or a quiesced snapshot so each restored database reference has the correct object version. Prevent object garbage collection from deleting versions needed by retained backups; restore the ledger and reconcile later independently preserved inbound messages without blindly duplicating imports. OM-BACKUP and OM-DB must design and test the consistency mechanism; daily scheduling alone does not provide one.

Regularly restore to a new server, verify keys, accounts, mail and Drive objects, replay and outbound queue behavior, and record the results. Loss of the VPS requires a restore before local services return. **Changes since the last successful backup can be lost**; independently preserved inbound items may be recoverable by replay if the archive and reconciliation proof succeed. Study more frequent intermediate backups or log-based recovery to reduce the loss window; do not promise a recovery objective before measuring it. A single VPS is not HA, even with external storage and backups.

## DNS, cutover and operating boundaries

Use explicit DNS records for `mail.<domain>` and later `calendar.<domain>` for their interfaces, with valid TLS certificates and correctly configured proxy trust. Leave any existing wildcard record intact; confirm actual DNS resolution and routing. Configure domain ownership, MX, SPF, DKIM, DMARC and any custom MAIL FROM records with the operator. Consolidate SPF mechanisms into the existing policy instead of adding a competing SPF record; validate lookup limits and all current senders. Before changing an existing MX, exercise the full inbound and outbound path on a controlled test domain or otherwise without diverting production mail, validate Bcc, replay and restore, and prepare a timed rollback with the previous MX and operational ownership recorded. Apply no DNS change until those tests pass and the operator authorizes the change.

The single VPS, B2, SES, AWS buffering, DNS and networks are separate dependencies. Mailbox/API reads can fail during VPS, network or B2 outages even while SES accepts and preserves new mail; sending may fail separately. No numerical availability guarantee is asserted. Monitor these outcomes independently and report failures rather than presenting an empty mailbox or a successful delivery. See the [risk register](../risks.md).
