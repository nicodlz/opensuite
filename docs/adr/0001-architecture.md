# ADR 0001: Mail engine, identity and reliability boundaries

- Date: 2026-10-29
- Status: Accepted as an architecture direction; implementation and provider proof are pending.
- Scope: New installations. The API skeleton is the only implemented component; the services below are planned.

## Decision

Pin Stalwart to **v1.0.1** for new deployments, using the explicit image tag `stalwartlabs/stalwart:v1.0.1` and a verified digest when assembling a release. The [v1.0.1 release](https://github.com/stalwartlabs/stalwart/releases/tag/v1.0.1) was published on 2026-10-28; its fixes include RocksDB concurrency and AArch64 failures and a configuration-file permissions issue. It also fixes several JMAP and calendar issues. [v1.0.0](https://github.com/stalwartlabs/stalwart/releases/tag/v1.0.0), published 2026-10-26, introduced a new database layout and does not support an in-place upgrade from v0.16.x. [v0.16.27](https://github.com/stalwartlabs/stalwart/releases/tag/v0.16.27), published 2026-10-18, is older; choosing it for a new installation would defer that migration. Sources accessed 2026-10-29. This is not a claim of maturity or upgrade safety: v1.0.1 is very new, and the exact image, backup, restore and protocol behavior must be tested before release. The release notes also say JMAP drafts and the JMAP Sent copy are stored without Stalwart's encrypt-on-append encryption; see the encryption decision below.

Use Stalwart for mailbox storage, JMAP, SMTP/IMAP and calendar/contact protocols. The application owns the browser session and orchestration; the critical mail service runs independently of the SPA and Drive. The standalone Drive service has separate storage and operational dependencies. Standard installations use one Stalwart instance with its internal directory and RocksDB, separate from the application's PostgreSQL. An optional HA profile requires a different shared-store design; it is not implied by Compose. Protocol evidence and its limits are in [Stalwart integration](../architecture/stalwart.md).

### Identity link

Better Auth is the application identity and session authority. Provision a separate Stalwart account and its aliases through the management API, and retain an immutable application-user-to-Stalwart-account mapping. Provisioning, updates, disablement and deletion must be reconciled, audited and retryable; disabling a user must revoke both application sessions and Stalwart credentials. Account deletion and mail retention require an explicit policy, not automatic destructive cleanup.

For application JMAP access, request a **server-generated, per-account Stalwart app password**, encrypt the one-time returned secret with an authenticated encryption key held outside the application database, and decrypt it only in the server-side adapter. The [app password documentation](https://stalw.art/docs/auth/authentication/app-password/) says creation for another account uses `x:AppPassword/set` with that account ID and requires `impersonate` and `sysAppPasswordCreate`; the secret is shown once. Those provisioning permissions are powerful: isolate that service and credential, audit its use, and evaluate the blast radius. If the creation response is lost, reconcile and revoke any orphan credential before replacement. Verify this flow and permission restrictions on the pinned image in OM-AUTH and OM-STALWART. Use separate, narrowly scoped server-side provisioning credentials, never a master or management credential in the browser. The browser receives only an application session cookie; each request is authorized against the user/account mapping before the server uses that account's credential. Do not derive the Stalwart secret from the user's Better Auth password. Separate, revocable credentials for IMAP, SMTP and DAV clients need a user-facing issuance, rotation and revocation flow. Secure key storage, rotation, recovery, credential compromise and lifecycle drift are implementation gates. Per-user credentials still grant mail access to the application server and may bypass Better Auth MFA if used outside the application; restrict direct client access and manage those credentials explicitly. [Stalwart authentication](https://stalw.art/docs/auth/authentication/) documents app passwords and supported protocols (accessed 2026-10-29).

Alternatives considered:

- **SQL directory over Better Auth tables:** [Stalwart's SQL directory](https://stalw.art/docs/auth/backend/sql/) uses configurable queries and verifies the returned password hash; it also needs recipient and alias queries. This would couple mail authentication and recipient lookup to the application database and its schema, password-hash compatibility and availability. Better Auth MFA/session policy would not automatically govern IMAP/SMTP/DAV password logins. It undermines the standard installation's mail isolation. Hash compatibility is unverified.
- **Stalwart OIDC directory:** [Stalwart's OIDC documentation](https://stalw.art/docs/auth/backend/oidc/) describes access-token validation and mapping; accounts must be provisioned before first sign-in to receive mail. OIDC could avoid storing an application mail password, but requires a compatible issuer, audiences, scopes, token lifecycle and clients, plus separate address provisioning and deletion reconciliation. Better Auth interoperability and mail-client support are unverified. Reconsider after an end-to-end spike.
- **Derived or shared user password:** deriving a mail credential from a login password couples rotation and exposes password-derived material to more systems; a reset or MFA change would not automatically revoke all direct protocol access. A random, encrypted credential has a clearer rotation boundary, at the cost of key management and server-side plaintext at use time.

All identity sources above were accessed 2026-10-29. The choice is architectural, not proof that any provisioning or authentication flow already works.

### Encryption and license

Require TLS for client and service connections, encryption of storage and backups, and separate key management with tested recovery. Server-side encryption and infrastructure encryption protect some storage and transport boundaries; the application, mail server, operators with key access, and delivery intermediaries may access plaintext. No end-to-end or zero-access property is claimed. The [v1.0.1 release notes](https://github.com/stalwartlabs/stalwart/releases/tag/v1.0.1) explicitly identify unencrypted JMAP drafts and Sent copies under its append-encryption behavior. Storage-layer encryption must cover these data; verify the actual configuration and restores (OM-STALWART, OM-BACKUP).

Stalwart source at the pinned tag identifies an `AGPL-3.0-only OR LicenseRef-SEL` choice in [source headers](https://github.com/stalwartlabs/stalwart/blob/v1.0.1/crates/jmap/src/email/import.rs); this decision assumes the AGPL option. OpenSuite is proposed as AGPL-3.0-or-later, subject to owner confirmation before publication. The AGPL-3.0 option and an AGPL-3.0-or-later component can be distributed under the common version 3 terms when combined, subject to the exact components and their licenses. A separate protocol connection alone does not settle whether a particular distribution is a combined work. Distributing Stalwart or modified versions entails the applicable source, notices and license obligations; AGPL section 13 also requires offering corresponding source to remote users of a modified program. Review the [license text](https://www.gnu.org/licenses/agpl-3.0.html) and all dependencies for the actual distribution and hosting model; owner/legal review remains open. Sources accessed 2026-10-29.

### Inbound and availability

SES → S3 → SNS → SQS → ingestion → Stalwart is a **candidate**, not an accepted production path. OM-INGEST must first prove raw message fidelity, recipient routing, authorization, size handling, failure recovery and ambiguous-import reconciliation against real Stalwart; a real AWS test requires explicit authorization. LocalStack and fixtures are useful but do not establish AWS behavior. If that proof fails, direct SMTP reception by Stalwart is the supported alternative to pursue, subject to its own operational validation.

Four different outcomes must be measured independently:

1. **Inbound acceptance:** an inbound SMTP receiver accepts responsibility for a transaction. It does not establish mailbox visibility.
2. **Durable preservation:** the message bytes _and sufficient recipient/routing metadata_ survive failure and can be recovered. Acceptance, an S3 object or a queue acknowledgement alone does not prove this end-to-end property.
3. **Mailbox/API availability:** authorized users can reach and read their mail through Stalwart and the application. It can be unavailable while incoming mail is retained elsewhere.
4. **Sending:** the application submits mail, Stalwart queues and relays it, and downstream delivery or failure is observed. Submission or provider acceptance is not proof of recipient delivery.

For optional HA, investigate separate failure domains, load balancing, shared PostgreSQL, object storage, Redis/Valkey and coordination, plus regional inbound reception and restore exercises. No availability percentage is promised. See [ingestion](../architecture/ingestion.md), [providers](../architecture/providers.md) and the [risk register](../risks.md).
