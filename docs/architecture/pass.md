# Esuno Pass: threat model and alias design

Date: 2026-10-30. This is a proposed design, not evidence of deployment or a security guarantee. **Nothing in this design or its implementation has been audited.** External sources below were accessed 2026-10-30. [ADR 0003](../adr/0003-pass.md) records the engine, configuration, compatibility evidence and storage proof gate. Task names identify work still required.

## Assets, actors and flows

Assets include vault item plaintext, master passwords, derived keys and 2FA recovery material on clients; encrypted vault records, attachments and Sends; authentication verifiers and session tokens; the server signing key, admin credential, PostgreSQL and SMTP credentials; alias keys, mappings and mail metadata; and backup snapshots and encryption keys. Actors include vault users, recipients and correspondents, authenticated alias users, operators, compromised or malicious clients, external attackers, hosting and relay providers, and an attacker with control of the B2 account. Users and operators are not interchangeable trust roles.

The browser extension, mobile/desktop app, CLI or web vault talks over TLS to Caddy and Vaultwarden on the dedicated Pass origin. Compatible clients perform vault encryption and decryption locally, then send encrypted item data and authentication material to Vaultwarden; it persists data in the dedicated PostgreSQL database and local volume. The web vault code is itself delivered by the server: a compromised server, Caddy, DNS/TLS path, supply chain or vault origin can serve malicious JavaScript that steals secrets at unlock. Server compromise also exposes authentication verifiers, ciphertext, user/device information and traffic metadata; it is not equivalent to a zero-knowledge guarantee against a malicious server. Attachment/Send content is client-encrypted where the relevant client protocol does so, but filenames, sizes, timing and other metadata may be visible. Never claim all metadata is encrypted. See Bitwarden's [encryption overview](https://bitwarden.com/help/what-encryption-is-used/) and [security white paper](https://bitwarden.com/help/bitwarden-security-white-paper/).

The Esuno SPA and API do not receive vault master passwords, unlocked keys, decrypted items or Vaultwarden session tokens by design. Vaultwarden does receive password-derived authentication material, ciphertext and operational metadata; the password itself is not intentionally transmitted. Do not log secrets, API keys, authentication headers, vault data or unencrypted exports in logs, telemetry, fixtures or error reports. A compromised endpoint or client can still expose plaintext, clipboard contents and autofill; phishing, malicious extensions, weak or reused master passwords and poor recovery handling remain risks. Encourage strong unique master passwords, separately protected recovery information and supported 2FA; loss of the master password or necessary recovery material can make vault data unrecoverable; do not claim rate limiting prevents offline attacks on stolen ciphertext.

The SPA shell uses its own Better Auth session for Esuno functions, including later alias management; it never uses that session to unlock the vault. Its generator runs locally and keeps generated values only in memory until dismissed, without analytics or API calls. It must avoid XSS, unsafe HTML, third-party scripts and unsafe storage. Opening the vault in a new tab isolates ordinary DOM and origin storage, not the shared host, browser, same-site cookie exposure or DNS. Use host-only cookies (`__Host-` where applicable), no `Domain` cookies, restrictive CSP and frame ancestors, and carefully review service workers, CORS and redirects. A compromised sibling origin can still conduct same-site attacks: enforce CSRF protection and origin checks on cookie-authenticated operations. PASS-WEB must test these boundaries and navigation.

## Administrative and infrastructure boundaries

Only Caddy serves the public vault; deny `/admin`, `/admin/` and all subpaths before proxying, including encoded and normalized path variations. No public container port or alternative public proxy may bypass the rule. Operator access is through a localhost-only listener or SSH tunnel with host/HTTPS handling validated end to end, and a separate strong admin password verified against the Argon2 PHC `ADMIN_TOKEN`. Keep the PHC and plaintext password outside Git; protect local files and sessions. Caddy overwrites the configured client IP header, and Vaultwarden trusts only the actual Caddy addresses. Test forged headers from outside and untrusted containers, admin routes, rate limits and proxy changes. The admin panel can change effective configuration, including security settings; `config.json` overrides environment values, so inspect effective configuration and restrict who can modify it. An admin or host compromise remains highly privileged.

The vault service only needs its database role, local volume and optional outbound SMTP credentials; do not share application, Drive, mail or backup credentials. Caddy and PostgreSQL are shared failure domains, as are the VPS, network and operator. Neither a healthy SPA nor API health proves vault usability. PASS-COMPOSE verifies startup, no SQLite fallback, migrations, access control, restarts, health and operation while API, Stalwart, Drive and ingest are stopped. SMTP outage affects invitation/recovery emails and any enabled email-based workflows; an established offline client may retain a cached vault, but offline availability is client-specific and must be tested.

Backups contain a consistent PostgreSQL snapshot, attachment/Send volume, configuration and signing keys. Encrypt with restic before B2 upload, separately protect and recover its key, limit B2 credentials, monitor retention and test restoration to an isolated clean host. Coordinate the database and objects, including deletes, so retained snapshots do not point at missing or later versions. A B2-account attacker may read encrypted snapshots and metadata, delete or roll them back, or disrupt recovery; encryption cannot ensure availability or freshness. Use immutability/versioning where supported and a separately administered second backup account or offline location, and test independent key and backup recovery. Host compromise may access plaintext configuration, keys and currently mounted credentials; backup encryption is not protection against that attacker. PASS-BACKUP must establish consistency, recovery and measured loss window.

## Alias lifecycle and mail boundaries

Aliases are mail features, not vault records. A dedicated API in Esuno's API owns them; it authenticates either a normal authorized Esuno session for management or a separate high-entropy, per-user, revocable alias API key for the compatible generator endpoint. A key is scoped only to alias creation for its owner, shown once, stored only as a keyed hash/HMAC with a separately protected server-side pepper (or an appropriate secure verifier), compared safely, rate-limited, and rotatable/revocable individually. Store identifier, owner, verifier, creation/last-use/revocation timestamps and scopes; never log the secret. A stolen key can create aliases and expose their target context until revoked, but cannot read vault data or administer the user's Esuno account. The Bitwarden client may retain the key in its own client settings; the shell must not collect Vaultwarden credentials. Alias request hostname and note can reveal a user's browsing or account associations to the API and operators; minimize retention, validate length and never treat them as trusted HTML or fetchable URLs.

The proposed data model has an immutable alias ID, normalized globally unique address, owner and destination Stalwart account ID, verified domain ID, optional website/label, state, timestamps, and provisioning/reconciliation status. Maintain separate domain ownership/verification and key records; never allow a caller to choose another user's mailbox or unverified domain. Use unique constraints and a durable intent/outbox for provisioning; mark active only after Stalwart and ingestion routing agree, retry idempotently and reconcile partial failures. Attach the address to the existing Stalwart account's `aliases` map via the authorized management adapter, not a separate mailbox; the [existing integration evidence](jmap-behaviour.md) describes `x:Account/set`. Do not give the public API a browser-accessible management credential.

Disabling an alias rejects new delivery and blocks its use as a sender after routing changes propagate; deletion first disables and removes the Stalwart alias and JMAP sending identity, then retains a tombstone to avoid accidental reassignment and preserve audit/reconciliation. Already accepted or queued messages follow a documented policy and may still arrive during propagation; neither action deletes existing mailbox messages. There is no atomic transaction across PostgreSQL, Stalwart and SES/ingest. Surface pending/failed states, retry and monitor drift. Account deletion, retention period and eventual reuse policy need an explicit operator decision; default to no reassignment. Current ingestion uses envelope recipients from SES, and may preserve a previously resolved destination on replay: disabled aliases must not silently invalidate already accepted durable work. Test disable/delete races, existing queued imports and direct SMTP separately.

Recipient identification must use trusted envelope-recipient data, including Bcc, not `To` or `Cc` alone. Preserve a per-message/per-destination alias association from the ingestion ledger through import to the authorized mailbox UI using a durable, reconciled mapping to the JMAP message ID; specify and test the association for multiple aliases to one mailbox, replays and duplicate imports. Direct SMTP delivery needs a separately proven way to retain equivalent envelope metadata; until then the UI must report the recipient as unknown rather than invent one. Protect these associations as mail metadata. See [ingestion](ingestion.md).

For replies, create or reconcile an authorized JMAP identity for each active alias and select it explicitly in `EmailSubmission/set`, with the From and envelope sender authorized for that account and domain. Verify reply headers, SMTP envelope, SES verified identity, DKIM/SPF/DMARC, Sent copy and all clients; do not promise anonymity, since existing thread headers, quoted content, signatures, return paths or correspondents may reveal the primary address. Disable/remove the identity with the alias, and reject stale or unauthorized identities server-side. JMAP identity and outbound relay behavior are **unverified** for this flow. Custom domains require proven ownership, operator-approved inbound routing and SES sender verification before activation; never alter DNS, MX or provider resources automatically as part of alias creation. Mail routing and outbound behavior remain subject to the existing [production proof gates](../adr/0002-production-target.md).

## Bitwarden forwarder contract

The contract below is source-inspected at Bitwarden clients tag `desktop-v2026.10.2`, not tested against every distributed client. [SimpleLogin forwarder](https://github.com/bitwarden/clients/blob/desktop-v2026.10.2/libs/tools/generator/core/src/integration/simple-login.ts), [addy.io forwarder](https://github.com/bitwarden/clients/blob/desktop-v2026.10.2/libs/tools/generator/core/src/integration/addy-io.ts), [request builder](https://github.com/bitwarden/clients/blob/desktop-v2026.10.2/libs/tools/generator/core/src/engine/rpc/create-forwarding-address.ts) and [context](https://github.com/bitwarden/clients/blob/desktop-v2026.10.2/libs/common/src/tools/integration/integration-context.ts) establish the following:

| Forwarder   | Request                                                                                                                                                                                                                                                                           | Successful response                                                                          |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| SimpleLogin | `POST <baseUrl>/api/alias/random/new` with optional `?hostname=<website hostname>`; `Authentication: <API key>`, `Content-Type: application/json`, `Accept: application/json`; JSON `{"note":"<localized generated-by text, optionally including website>"}`.                     | HTTP 200 or 201, JSON `{"alias":"address@example.com"}`; client reads `alias`.               |
| addy.io     | `POST <baseUrl>/api/v1/aliases`; `Authorization: Bearer <API key>`, the same JSON content and accept headers; JSON `{"domain":"<configured alias domain>","description":"<localized generated-by text, optionally including hostname>"}` (description limited to 200 characters). | HTTP 200 or 201, JSON `{"data":{"email":"address@example.com"}}`; client reads `data.email`. |

Both definitions permit an optional self-hosted `baseUrl` (`selfHost: "maybe"`); an empty value uses the vendor default. This decision implements **only the SimpleLogin subset**, not addy.io or the full SimpleLogin API. Configure the client under username generator → Forwarded email alias → SimpleLogin with the Esuno HTTPS server base URL and its alias key. Publish the exact endpoint at the appended path with no redirects; a base URL must not accidentally cause duplicated `/api` segments. The endpoint accepts `Authentication` as the key, validates optional hostname and note as untrusted bounded metadata, derives the user solely from the key, creates an alias in an authorized verified domain, and returns 200/201 with the top-level `alias` only after activation. Return appropriate 401 for invalid/revoked keys, 403 for forbidden operations, and bounded 4xx/5xx errors without secrets. Define retry behavior and reconcile ambiguous failures: this client sends no idempotency key, so do not promise exactly-once creation or blindly retry a timed-out request. Provide management visibility for possible orphan aliases.

The cross-origin endpoint uses **API key only, no cookies or application sessions**; ignore cookies for authorization and reject cookie-only requests. Handle `OPTIONS` preflight without authentication, allowing only the configured web-vault origin and `POST, OPTIONS` and headers `Authentication, Content-Type` (and `Accept` if requested), with `Vary: Origin`; never set `Access-Control-Allow-Credentials`. Restrict origins where the browser supplies them, while allowing non-browser clients and extension contexts only after explicit compatibility testing; CORS is not authentication. The Vaultwarden web vault may need `ALLOWED_CONNECT_SRC` set to the exact HTTPS API origin in its CSP. Test preflights, client extension origins, revoked keys, CSRF isolation, malformed payloads, concurrent creation and absence of credentials in logs. PASS-ALIAS and PASS-ALIAS-WEB own API and user/key lifecycle tests; PASS-COMPAT tests the real clients. The alias API receives no vault item data by design, although the optional hostname and note disclose context.
