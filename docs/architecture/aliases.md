# Mail aliases

An email alias is a reserved address on a verified installation domain. It belongs to one Esuno user and points to that user's existing Stalwart account. This service is independent of any password vault; it receives no vault keys or vault contents. The API requires an active mailbox, and does not create or modify domains, DNS, MX records or SES rules.

The address reservation is unique, case insensitive and permanent. Deletion keeps a tombstone and its underlying address reservation, so it cannot be given to another user, including through the administrator's address-management API. Tombstones retain their `Address` rows and prevent domain removal; a domain selected as any user's default also cannot be removed. Domain removal reserves the domain before changing SES; if interrupted, retry removal to reconcile the pending reservation. Disabled and deleted aliases are removed from the Stalwart account; enabling restores them. A database reservation is committed before contacting Stalwart. Pending operations are retried by the API's reconciliation job at startup and every minute. A busy account lease returns the reserved alias with `ready=false`; other operations that cannot be confirmed return an error and remain pending; retry creation with the same `requestId` to recover the same address. Session creation requires a `requestId`; use a fresh one for a new alias. Bitwarden does not send an idempotency key, so retrying an ambiguous compatibility request can create an additional alias. A randomly generated local part contains 96 bits of randomness, optionally preceded by a validated custom prefix. The active per-user cap includes disabled aliases and defaults to 1,000; a lifetime cap of ten times that value includes tombstones. Key creation is limited to 20 active and 200 lifetime keys; set `ALIAS_PER_USER_CAP` to a positive integer to change it. The stock Compose API environment does not pass this variable; use a local Compose override to supply it. Creation has in-memory per-user limits; the compatibility endpoint additionally limits each key and IP. Alias submissions are limited to 30 per user per minute and each attempt records an audit event without message content. These limits are per API process and reset on restart, so multi-instance installations need shared rate limiting.

Stalwart 1.0.1 exposes an identity for an account alias automatically and removes it when the alias is removed. The API confirms that identity during reconciliation. A per-user expiring lease serializes account alias updates without holding a database connection during Stalwart calls; a revision check makes stale results pending again. A domain that loses verification is detached once and requeued when verification returns. An alias whose owner or mailbox is inactive or missing is marked suspended and is requeued when that state changes. The last mailbox account ID is retained to detach its aliases when the mailbox link is deleted or replaced. Mail draft creation accepts an optional `from` address and permits an enabled, ready alias owned by the caller; submission uses the matching identity and envelope sender. This is tested against local Stalwart, not against the production SES relay. Replies are ordinary mail from the alias and do not implement SimpleLogin reverse aliases or hide addresses quoted in message bodies or headers.

## API and Bitwarden

Session-authenticated procedures under `/api/aliases` provide list/search, create, update, enable, disable, delete, address matching, default-domain get/set and key create/list/revoke. The matching procedure accepts addresses extracted by the client from the stored message's To, Cc, Delivered-To and X-Original-To headers and compares them with the caller's aliases, including tombstones. It cannot identify a Bcc recipient when the envelope address is absent from the stored MIME. A user's default domain must be set before using the compatibility endpoint. The API returns an alias key secret only once; it stores a SHA-256 digest of the random 256-bit secret, not plaintext. Revocation prevents further requests.

1. Use the Esuno alias API to select a verified default domain and create an alias API key. Copy its secret immediately.
2. In a Bitwarden client, open Generator, select Username, then **Forwarded email alias** and **SimpleLogin**.
3. Paste the alias key and set the self-hosted Server URL to the Esuno public origin, such as `https://mail.example.test`, without `/api`.
4. Generate a username. The integration sends the current website hostname when available; Esuno stores it with the generated alias.

The public compatibility endpoint is `POST /api/alias/random/new` (Caddy strips `/api`, so the API listens at `/alias/random/new`). It accepts the key only in `Authentication`, an optional `hostname` query and a JSON `{ "note": "..." }`; it returns `201 { "alias": "..." }`. Errors use `{ "error": "..." }` and non-success status codes. CORS is restricted to this endpoint, allows any origin without credentials, and permits `Authentication` and `Content-Type`. Session cookies cannot authorize it. This is a limited username-generator integration, not a complete SimpleLogin API.

Contract checked against Bitwarden clients commit [`96f157b3e73f71b966505f15e6b236ab1298fc73`](https://github.com/bitwarden/clients/tree/96f157b3e73f71b966505f15e6b236ab1298fc73): [`simple-login.ts`](https://github.com/bitwarden/clients/blob/96f157b3e73f71b966505f15e6b236ab1298fc73/libs/tools/generator/core/src/integration/simple-login.ts) defines the path, `hostname`, body, authentication header and `alias` result; [`create-forwarding-address.ts`](https://github.com/bitwarden/clients/blob/96f157b3e73f71b966505f15e6b236ab1298fc73/libs/tools/generator/core/src/engine/rpc/create-forwarding-address.ts) specifies POST and JSON headers. The client reads JSON only on 200 or 201.

## Inbound behavior and limits

The managed-domain provider adds the domain name to the configured SES receipt rule, making that rule domain-wide when domain management has provisioned it. Separately configured receipt rules may instead list individual addresses; alias creation does not inspect or change them. Verify the actual rule covers the domain before relying on new aliases. Ingestion reads SES envelope `receipt.recipients`, maps enabled and ready address records to the mailbox account ID and imports via JMAP. The worker delivers with the mailbox's stored credential when it has the mailbox key (see [ingestion](ingestion.md)); otherwise the mailbox account ID must be present in its separately configured `INGEST_DESTINATIONS`, with valid credentials and quarantine mailbox. Otherwise import fails and follows the existing retry/recovery path. Messages go to the configured quarantine mailbox according to the [verdict policy](ingestion.md#contract-and-routing).

For a disabled or deleted alias with no independent static route, newly resolved SES recipients are unknown. After SES acceptance, ingestion holds the recipient and retains the message object; it does not bounce the sender. Replay rechecks the address. If a disabled alias is re-enabled and ready, replay within the hold window can deliver the held mail; a deleted alias is tombstoned and cannot be re-enabled or reused. An operator can reject a held recipient, or replay expires it after `INGEST_HOLD_DAYS` (14 days by default, counted from SES receipt); neither sends a bounce. The object is deleted only after all recipients are finished, and versioned storage may retain older bytes. A pending enable is likewise unknown until reconciled. See [ingestion recovery](ingestion.md#operator-recovery) for the hold, expiry, retention and operator procedure.

Direct SMTP to Stalwart no longer resolves an alias after removal. Previously resolved ledger entries keep their recorded destination across retries and may still import after disable or deletion. Static `INGEST_ROUTES` are independent and can still route an alias; do not configure alias addresses there. Fencing static routes and already-resolved deliveries would require a follow-up change if immediate revocation of every in-flight message is required. These behaviors do not establish real AWS delivery or recovery; validate the installation's SES, archive and worker configuration separately.
