# SES inbound ingestion

The implemented worker consumes a **raw SNS delivery** SQS body containing an SES S3-action notification, archives that body, records the message and recipient states in PostgreSQL, reads the original S3 bytes once, uses HTTP upload, and calls `Email/import` separately for each destination account. Recipients are processed sequentially to bound memory; the original message and an upload buffer still need to fit in worker memory. This is a local implementation, not a production go/no-go proof: real SES, SNS, SQS, S3, B2, the production proxy, credentials, permissions and failure behavior have not been exercised. Real AWS calls require separate authorization.

## Contract and routing

AWS describes `receipt.recipients` as “the envelope RCPT TO addresses” matched by the rule, and the S3 action provides the “raw, unmodified email”. See [notification contents](https://docs.aws.amazon.com/ses/latest/dg/receiving-email-notifications-contents.html) and [S3 action](https://docs.aws.amazon.com/ses/latest/dg/receiving-email-action-s3.html). Fixtures follow these descriptions, not captured AWS events. `mail.messageId` is the SES identifier; `receipt.action.objectKey` is used as supplied, including any prefix. Processing time accepts both the documented string and the number in AWS examples. All five verdicts must be present and valid: all PASS delivers to inbox; FAIL, GRAY or PROCESSING_FAILED imports into the configured quarantine mailbox. Unknown recipients are held after SES acceptance, not bounced: the message and its object are kept until the address is provisioned, an operator rejects it, or replay expires the hold. Aliases are normalized case-insensitively and grouped by configured destination, including Bcc and multiple domains.

Configure one receipt rule whose notification covers **all intended envelope recipients** for a message. Notifications from separate rules can arrive after the first notification has been processed and its buffer object deleted; the worker cannot infer future recipients. Queue and SNS policies must restrict publishers, raw delivery must be enabled, and the configured bucket, topic and buffer prefix must match. Do not enable SES client-side message encryption: ordinary S3 GET does not decrypt it. Transport, storage encryption, access control, backups, retention and restore procedures remain operator responsibilities.

## Durability and failure handling

A notification is copied to the configured S3-compatible archive before PostgreSQL processing or SQS acknowledgement. This protects it after the worker has received it, including after a later SQS expiry. **It does not protect a notification lost or expired before the worker receives it.** An independent durable SNS subscriber/archive and its recovery path are required to close that gap before production. Archive and buffer must be independently durable, protected from deletion and retained long enough for recovery, and the archive at least longer than the hold window (`INGEST_HOLD_DAYS`): replay walks archived notifications, so a held message whose notification expires first is stranded with its object; B2 has not been tested. If the archive is unavailable, the message is retried and not acknowledged.

The ledger stores the notification as JSON and records each resolved destination and its envelope addresses. A redelivery uses those durable destinations even if routing has changed. An atomic claim records an owner and a ten-minute lease; the worker renews it every minute. Immediately before sending `Email/import`, it records `importStartedAt` under the current owner. An expired new claim with no import start becomes retryable; an expired claim with an import start becomes `uncertain`. Existing in-flight and uncertain rows at migration are marked legacy and remain uncertain even if their claim has no timestamp, because the old worker did not record the start marker. Conditional updates fence expired owners. An unknown recipient is durably `held`, with its envelope addresses, and is not terminal. Each replay resolves routes again; when a held address has since become known (a new mailbox or alias), the same locked transaction moves it to that mailbox's recipient and marks the held row `rerouted`, so the message is imported once and never twice into a mailbox that already has it. A message whose only unfinished recipients are held is acknowledged on SQS with state `held`; the archived notification and the scheduled replay carry it forward. The buffer is removed only after every recipient is finished: imported (including quarantine), `rerouted`, or `rejected` by an operator or expiry. Deletion and SQS acknowledgement failures can be retried safely.

JMAP and PostgreSQL cannot commit atomically. A lost or timed-out import response becomes `uncertain` and leaves the SQS message unacknowledged and the buffer intact. A confirmed connection refusal before the first request is retryable. A proxy 502, 503 or 429 is ambiguous unless the proxy provides trustworthy proof that the upstream could not have accepted the body; ordinary HTTP status alone provides no such proof. Imports carry a deterministic per-recipient keyword and the SES mail timestamp as `receivedAt`. On redelivery or replay, the worker searches the target account for that keyword and confirms the destination mailbox, timestamp at Stalwart's one-second precision, Message-ID when present, and size and SHA-256 of downloaded original bytes. One or more confirmed matches complete the recipient. Multiple matches also emit an error-level `ingest_duplicate` alert containing the hashed recipient key and count; investigate and remove duplicates deliberately. Keyword candidates with changed metadata or bytes require investigation rather than automatic retry.

When the keyword query returns zero candidates, the worker waits at least 15 minutes after the import start (longer than the ten-minute lease plus the 120-second JMAP deadline) before conditionally making the recipient retryable. This is a practical recovery tradeoff, not an exactly-once guarantee: a delayed upstream commit can still produce a duplicate. The keyword lets a later reconciliation detect it, but monitor `ingest_duplicate` and the mailbox. Permanent JMAP rejections such as `invalidEmail` and `forbidden` are stored separately and neither ordinary processing nor replay resets them. Infrastructure failures do not consume the per-recipient attempt budget. Legacy imports without the keyword require the operator workflow below.

SQS visibility starts at five minutes and is extended every minute while handling a message. Failure delays start at one minute and double to an hour; AWS and local queues allow 100 receives and retain messages for 14 days. A prolonged outage can still exhaust retention or reach the DLQ, so alert on both and retain the archive. JMAP requests have a 120-second deadline including response bodies; buffer and archive SDK clients use connection and request deadlines, and S3 body reads have a deadline. Timeout during import is ambiguous. Configure and monitor the DLQ, backlog and replay scheduler independently.

## Running and recovery

Run `pnpm --filter @opensuite/ingest start` for the worker or `pnpm --filter @opensuite/ingest start replay` for reconciliation. Supply `DATABASE_URL`, `INBOUND_BUCKET`, `INBOUND_QUEUE_URL`, `INBOUND_TOPIC_ARN`, `INBOUND_BUFFER_PREFIX`, `ARCHIVE_BUCKET`, `ARCHIVE_PREFIX`, `INGEST_ROUTES` and `INGEST_DESTINATIONS`. Routes are JSON objects with `address` and stable `destination`; destinations have `id`, JMAP `origin`, `authorization` and the quarantine mailbox ID `quarantineMailbox`. When Stalwart advertises a public URL but the worker must use an internal origin, set `rewriteSessionUrls: true` on that destination. This server-side opt-in rewrites the advertised API, upload and download origins to the configured JMAP `origin`, retaining their paths and queries; only use it for a trusted server. Without it, cross-origin endpoints and redirects are rejected. Store these credentials in a protected secret store and inject them only into the worker. `AWS_REGION` defaults to `eu-north-1`; SDK default credentials are used for the buffer and queue. `AWS_ENDPOINT_URL` enables LocalStack. `ARCHIVE_ENDPOINT_URL`, `ARCHIVE_REGION`, `ARCHIVE_ACCESS_KEY_ID` and `ARCHIVE_SECRET_ACCESS_KEY` configure the archive independently. `INGEST_MAX_ATTEMPTS` defaults to 5, `INGEST_AGE_SECONDS` to 3600 and `INGEST_HOLD_DAYS` to 14 (1–365).

Replay lists archive notifications and buffer objects, resets retry counts only for non-permanent failed recipients, and skips ledger messages already marked imported. Replay never rewrites archive objects. It continues if buffer listing fails but reports a failure because orphan detection was incomplete. It emits `ingest_buffer_without_notification` for orphan objects and `ingest_notification_old` for old archived notifications whose buffer remains. The buffer is deleted before a message is marked imported; if deletion fails, the message stays `failed` and the next SQS redelivery or replay retries the deletion without importing again. Replay never guesses envelope recipients or verdicts from MIME. Run replay periodically through an external scheduler and alert on its failures, the DLQ and backlog age.

The worker stops polling on SIGTERM or SIGINT, aborts an outstanding receive and waits for any received message and its visibility heartbeat to finish before closing connections. Compose gives the ingest service two hours to drain; processing has no absolute upper bound on recipient count or remote service behavior, so operators must set a longer grace period if their maximum workload can exceed that window. A forced shutdown still relies on lease expiry and reconciliation.

### Operator recovery

Run these commands in the ingest container with its normal configuration and restricted database and mailbox credentials. The list returns at most 200 rows and a `nextCursor`; pass that cursor to list the next page. Results contain sensitive message and destination identifiers, so protect command output. Live claims cannot be resolved; expired claims are first transitioned by the command.

```sh
node apps/ingest/src/main.ts operator list
node apps/ingest/src/main.ts operator list <nextCursor>
node apps/ingest/src/main.ts operator inspect <recipientKey>
node apps/ingest/src/main.ts operator resolve <recipientKey> imported <remoteId> <operator> '<reason>'
node apps/ingest/src/main.ts operator resolve <recipientKey> retry - <operator> '<reason>'
node apps/ingest/src/main.ts operator reject <recipientKey> <operator> '<reason>'
```

`inspect` reads the retained original buffer and searches the mailbox. For legacy rows it searches by the original Message-ID and verifies the full size and SHA-256 of downloaded raw messages, regardless of mailbox, keyword or received timestamp; a missing Message-ID or unavailable original requires manual investigation and cannot be automatically resolved by this command. For newer rows it uses the keyword and normal verification. `imported` accepts only an ID returned by a fresh verified search. `retry` requires a fresh search with no verified matches; examine mailbox history first, since an unobserved delayed import or modified message can still duplicate. For multiple matches choose an existing verified ID and investigate the extra copies. The command atomically records the operator, reason, prior state, action, remote ID and time in the append-only `InboundResolutionAudit` table with the state change, and refuses a row that changed during inspection. Operator identities are supplied by the caller, so authenticate and restrict command access and retain database audit records. After a resolution, redrive the SQS item or run replay to finish message-level state and buffer cleanup. Permanent failures may be retried only through this explicit workflow after the cause is addressed.

The list also shows `held` recipients; `operator list held [cursor]` shows only those, and the default `operator list` omits them so that rows needing a decision are not buried (their `destination` is the unknown address itself, so protect the output). To deliver one, provision the address (mailbox or alias) and run replay. To give up on one, run replay first (the address may have been provisioned since), then `reject` it: only a `held` row can be rejected, the command takes the same message lock as routing, the change and the operator, reason and prior state are recorded atomically in `InboundResolutionAudit`, and the next replay deletes the original object once no other recipient needs it. Rejection does not notify the sender.

**Hold window.** Anyone can send to any address at an accepted domain, so held mail is bounded by `INGEST_HOLD_DAYS` (default 14), counted from the SES receipt time with the worker's clock (keep it synchronized); the routing decision is taken under the message lock. Within the window, an address provisioned later receives every message held for it, with the original dates; beyond it, the address is never routed and replay rejects the held recipient automatically, recorded in `InboundResolutionAudit` as operator `system:expiry`, action `expire`, then deletes the object. Until then the full raw messages of these third parties, including ones with failing verdicts, stay in the buffer. Deleting a buffer object only adds a delete marker in the versioned buffer, so the raw message remains as a noncurrent version for the bucket's noncurrent-version expiry (30 days in the provided configuration). The SES notification, which carries the envelope recipients and the headers SES includes (such as From, To and Subject), stays in the `InboundMessage` ledger and therefore in database backups indefinitely, and in the archive until its retention ends; neither holds the raw body. Choose the window with that privacy cost in mind, and mind that reusing an address for a new person within the window delivers the previous holder's pending mail. Each replay reprocesses every held message and emits `ingest_notification_old` for those older than `INGEST_AGE_SECONDS`, so expect that event for held mail.

Structured JSON log events are the metrics interface: `ingest_imported` includes `delaySeconds`, and `ingest_failure`, `ingest_duplicate`, `ingest_held`, `ingest_held_expired`, `ingest_notification_old` and `ingest_buffer_without_notification` include per-process event counts. Export and aggregate these logs as counters and delay distributions; counts reset on restart. Worker logs exclude recipient addresses, message IDs and object keys; access should still be restricted. See [observability](../operations/observability.md) for the status job and alert delivery.
