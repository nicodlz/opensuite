# SES inbound ingestion

The implemented worker consumes a **raw SNS delivery** SQS body containing an SES S3-action notification, archives that body, records the message and recipient states in PostgreSQL, uploads the original S3 bytes with the existing JMAP client's `Blob/upload` or HTTP upload, and calls `Email/import` separately for each destination account. Large messages use HTTP upload to avoid the JSON/base64 request size limit. This is a local implementation, not a production go/no-go proof: real SES, SNS, SQS, S3, B2, the production proxy, credentials, permissions and failure behavior have not been exercised. Real AWS calls require separate authorization.

## Contract and routing

AWS describes `receipt.recipients` as “the envelope RCPT TO addresses” matched by the rule, and the S3 action provides the “raw, unmodified email”. See [notification contents](https://docs.aws.amazon.com/ses/latest/dg/receiving-email-notifications-contents.html) and [S3 action](https://docs.aws.amazon.com/ses/latest/dg/receiving-email-action-s3.html). Fixtures follow these descriptions, not captured AWS events. `mail.messageId` is the SES identifier; `receipt.action.objectKey` is used as supplied, including any prefix. Processing time accepts both the documented string and the number in AWS examples. All five verdicts must be present and valid: all PASS delivers to inbox; FAIL, GRAY or PROCESSING_FAILED imports into the configured quarantine mailbox. Unknown recipients are recorded as rejected after SES acceptance, not bounced. Aliases are normalized case-insensitively and grouped by configured destination, including Bcc and multiple domains.

Configure one receipt rule whose notification covers **all intended envelope recipients** for a message. Notifications from separate rules can arrive after the first notification has been processed and its buffer object deleted; the worker cannot infer future recipients. Queue and SNS policies must restrict publishers, raw delivery must be enabled, and the configured bucket, topic and buffer prefix must match. Do not enable SES client-side message encryption: ordinary S3 GET does not decrypt it. Transport, storage encryption, access control, backups, retention and restore procedures remain operator responsibilities.

## Durability and failure handling

A notification is copied to the configured S3-compatible archive before PostgreSQL processing or SQS acknowledgement. This protects it after the worker has received it, including after a later SQS expiry. **It does not protect a notification lost or expired before the worker receives it.** An independent durable SNS subscriber/archive and its recovery path are required to close that gap before production. Archive and buffer must be independently durable, protected from deletion and retained long enough for recovery; B2 has not been tested. If the archive is unavailable, the message is retried and not acknowledged.

The message ledger stores the notification and object locator; recipient rows use a unique hash of the SES ID and resolved mailbox (or unknown address). An atomic claim prevents concurrent imports for the same destination. The worker records import or quarantine before deleting SQS; an unknown recipient is durably rejected and its object retained. The buffer is removed only when all known ledger recipients have confirmed imports, including imports to quarantine. The queue is retried with bounded exponential visibility delays; configure the production queue and DLQ redrive policy and 14-day retention independently. Invalid notifications, archive failures and transient failures are retried to the DLQ. The local setup uses five receives and 14 days for both queues. There is no automatic visibility extension; provision visibility for the largest message and monitor long operations.

JMAP and PostgreSQL cannot commit atomically. If an import response is lost, the recipient is `uncertain`; a crash after claiming but before the durable result leaves `importing`. Neither is automatically retried. The worker retains the source, emits an alert event, and an operator must inspect the mailbox and reconcile the record before retrying. JMAP `Email/import` itself creates duplicates; no exactly-once guarantee is claimed. Successful durable state before SQS deletion prevents ordinary queue redelivery from reimporting. Database and archive restoration, competing workers, lost import responses, and cross-rule behavior require further proof.

## Running and recovery

Run `pnpm --filter @opensuite/ingest start` for the worker or `pnpm --filter @opensuite/ingest start replay` for reconciliation. Supply `DATABASE_URL`, `INBOUND_BUCKET`, `INBOUND_QUEUE_URL`, `INBOUND_TOPIC_ARN`, `INBOUND_BUFFER_PREFIX`, `ARCHIVE_BUCKET`, `ARCHIVE_PREFIX`, `INGEST_ROUTES` and `INGEST_DESTINATIONS`. Routes are JSON objects with `address` and stable `destination`; destinations have `id`, JMAP `origin`, `authorization` and the quarantine mailbox ID `quarantineMailbox`. Store these credentials in a protected secret store and inject them only into the worker. `AWS_REGION` defaults to `eu-north-1`; SDK default credentials are used for the buffer and queue. `AWS_ENDPOINT_URL` enables LocalStack. `ARCHIVE_ENDPOINT_URL`, `ARCHIVE_REGION`, `ARCHIVE_ACCESS_KEY_ID` and `ARCHIVE_SECRET_ACCESS_KEY` configure the archive independently. `INGEST_MAX_ATTEMPTS` defaults to 5 and `INGEST_AGE_SECONDS` to 3600.

Replay lists archive notifications and buffer objects, resets retry counts only for definitively failed recipients, and reprocesses archived envelopes. It emits `ingest_buffer_without_notification` for orphan objects and `ingest_notification_old` for old archived notifications whose buffer remains. It never guesses envelope recipients or verdicts from MIME. An orphan requires an independently recovered SES notification or operator intervention. Rejected, uncertain and importing records are not reset automatically; investigate these before any manual ledger change. Run replay periodically through an external scheduler and alert on its failures, the DLQ and backlog age.

Structured JSON log events are the metrics interface: `ingest_imported` includes `delaySeconds`, and `ingest_failure`, `ingest_rejected`, `ingest_notification_old` and `ingest_buffer_without_notification` include per-process event counts. Export and aggregate these logs as counters and delay distributions; counts reset on restart. Logs can contain recipient addresses and object keys and require restricted access. Logging alone does not establish an alerting pipeline.
