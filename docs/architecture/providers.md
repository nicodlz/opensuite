# Provider boundaries and availability

Date: 2026-10-29; updated for the current checkout. Inbound, outbound and domain adapters exist, but provider behavior is not proven. The HA profile remains a proposal.

## Boundaries

- **Inbound:** A provider adapter normalizes authenticated receipt metadata, original-message location and verdicts into durable per-recipient processing. SES S3/SNS/SQS is the planned [production target](../adr/0002-production-target.md), requiring the [ingestion proof](ingestion.md). Direct Stalwart SMTP is the fallback to validate if the proof fails. A local substitute tests our code, not an AWS service guarantee.
- **Outbound:** Stalwart is responsible for the mail queue and SMTP delivery. A configuration adapter selects SES SMTP relay, another authenticated SMTP relay, or direct SMTP. Track submission, queued, relay accepted, temporary failure, permanent failure and downstream feedback separately. Validate sender identities, credentials, rate limits, retries and bounce handling; do not declare recipient delivery from a successful JMAP submission or SES acceptance. AWS documents a 40 MB maximum for SES SMTP after encoding and regional sending quotas in [SES quotas](https://docs.aws.amazon.com/ses/latest/dg/quotas.html), accessed 2026-10-29.
- **Storage:** Mail, inbound spool, backups and Drive have distinct access, lifecycle and recovery policies even if they use the same S3-compatible implementation. Drive failures must not block mail. Isolation at the service boundary does not protect against a shared physical provider outage or exhausted host resources; test and monitor those dependencies.
- **DNS and domain onboarding:** Present ownership verification and records for MX, SPF, DKIM, DMARC and MAIL FROM, then check actual propagation and provider verification before declaring a domain usable. DNS/provider modifications require explicit operator authorization. SES identity signing and Stalwart DKIM management are separate choices; document which signs each outbound route.

## Deployment and service outcomes

The single-VPS target prioritizes simplicity: Stalwart uses persistent RocksDB; the application and Drive use separate PostgreSQL databases; B2 stores mail blobs, Drive objects and encrypted backups with separate access. LocalStack substitutes for external AWS services in development only. The production integration is not deployed. It has single-host failure modes and requires tested backup and restoration. No HA claim follows from service restarts.

An optional HA design needs independent failure domains, replicated shared stores and coordination, redundant ingress, recovery and monitoring. [Stalwart's cluster requirements](https://stalw.art/docs/cluster/), accessed 2026-10-29, describe the shared PostgreSQL/S3-compatible/Redis components and coordinator needed for the proposed profile; validate the selected versions, edition and actual failover. Regional SES reception, DNS and object replication are separate decisions, not automatic consequences of a Stalwart cluster. Recovery objectives and service-level targets must be measured and agreed by operators; no numeric availability guarantee is asserted.

Assess four outcomes separately: SMTP acceptance, durable preservation of bytes **and** envelope metadata, mailbox/API access, and outbound delivery. An outage can affect any one without affecting all others. Alert on backlog age, preservation and restore failures, mailbox access, outbound queue and delivery failures; design error handling so failures never masquerade as an empty mailbox or successful delivery.
