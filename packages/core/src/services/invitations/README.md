# Invitation sender verification

Invitation reads return `senderStatus` as `verified` or `unverified`. Verification uses the ingestion ledger for the same mailbox and immutable JMAP message: the received message must have a passing aligned SES DKIM or DMARC verdict and must not have been quarantined. The message must contain DKIM-Signature headers whose `d=` domains all share the organizer's registrable domain, using the Public Suffix List including private suffixes; this permits subdomains while separating unrelated tenants. Every signature must be well formed and aligned because the SES summary does not identify which signature passed. Signatures with a body-length (`l=`) tag are unverified because the calendar part could be unsigned. Missing, ambiguous or mixed signing domains are unverified. Message-supplied Authentication-Results headers are not used as proof. Exactly one From header with one address must equal the single iTIP organizer. For an existing series, that organizer must also equal the organizer already stored for that series. A message with missing, failed, untrusted, or mismatched provenance is unverified; message-supplied authentication headers are not trusted.

`/invitations/act` accepts verified requests and cancellations. An unverified new REQUEST can be accepted, tentatively accepted, or declined only by an explicit `/invitations/confirm` call after the user has seen the unverified sender. Confirmation cannot apply an unverified update or cancellation to an existing event. Unverified messages remain readable, including when Calendar or the authentication lookup is unavailable. Both actions require the normal authenticated, same-origin API session and recipient authorization.

Organizer revisions are checked against the last accepted organizer version and merged with the current Calendar object. Local title, description, location, time, recurrence rule and status are retained when the organizer has not changed those fields; an organizer change takes precedence for the same field. Other unexposed properties and alarms are preserved when the revision omits them. Each operation stores the Calendar snapshot it read and uses the Calendar state as a write precondition. A later local edit causes a conflict instead of being overwritten, and a fresh action can retry against the new snapshot.

The Stalwart integration tests use local Google-style iTIP fixtures and trusted local ingestion records. Real Google interoperability has not been proved; the mail-reader interface is separate work.

Organizer operations use `/invitations/organize` with an authorized sending identity, an event and its attendees. Each request ID reserves the calendar revision and one delivery per recipient before making external writes. Repeating the same request ID returns or reconciles that operation; reusing it with different input is a conflict. The organizer endpoints handle updates and cancellations of organized events. Ordinary calendar editing rejects those events so it cannot silently skip invitations; after cancellation finishes, the event can be deleted normally. Calendar imports do not invoke the organizer endpoint and do not send mail.

Each recipient receives an individual iTIP REQUEST or CANCEL with shared event fields; local alarms, attachments and private extension properties remain on the calendar event and are omitted from the message. A submission that may already have reached the mail server remains pending until its matching submission can be found; it is never blindly repeated. A calendar write is retried only when its original state is still present, using a JMAP state precondition; a result that cannot be recognized or safely retried stays pending. A submission known to have failed before its request was sent can be retried safely; a definitive rejection is reported as failed and releases the series. A bounded background job revisits old pending operations, while `/invitations/organized/reconcile` reports or resumes their safe steps. Attendee responses and the pending operation ID are exposed by `/invitations/organized/status`; replies to earlier revisions are not shown as responses to the current revision. Reply processing checks the immutable imported-mail ledger and the same local signing-domain alignment and quarantine rules as received invitations, then matches the sender, organizer, event, sequence and recurrence. Unverified messages do not change attendee state. Safe external Calendar edits are adopted when organizer, attendee identities and attendee participation are unchanged. Scheduling changes require an explicit organizer edit before reply processing resumes. The background scan starts with mail imported around or after the first organized event, shares bounded batches across accounts, and stops retrying permanently unverified or conflicting messages; verified replies received during a pending operation are revisited when that operation completes. `/invitations/organized/unverified` lists unverified reply message IDs for inspection, and `/invitations/organized/reply` returns their parsed contents and verification result. A real Google interoperability proof remains separate.
