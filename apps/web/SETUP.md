# Administrator setup wizard

Sign in as the bootstrap administrator and open `/setup`. The wizard reads live server state; the development server uses synthetic data and must not be used to operate a real installation. The last visited step is remembered in the current browser session. Domains and accounts are read from the server when returning. A test submission is only recorded for the current page; it does not prove delivery.

The wizard does not bootstrap authentication, install services or change DNS. Follow the authentication bootstrap and mailbox provisioning instructions in the development guide first. Mailboxes are provisioned for `MAIL_DOMAIN`, the domains in `MAIL_DOMAINS` and any managed domain whose removal has not started, even before its DNS is verified; any other address is refused. Enable and configure the domains provider and mail API separately as documented in the domain and development guides. A domain's DNS check requires the MX to match; for an existing domain that means it cannot show fully verified before an owner-approved MX cutover. Validate all other records and mail flow separately before that decision. Creating a domain may update SES identity and receipt-rule configuration; it never publishes DNS.

The setup API reads API readiness and the internal Drive readiness endpoint. The object storage result is Drive's bucket probe, not Stalwart's blob store or a backup. SES relay status uses the domain provider’s `DOMAINS_STALWART_ORIGIN`, `DOMAINS_STALWART_USER`, and `DOMAINS_STALWART_PASSWORD_FILE` management credential and network access; it is unavailable when that provider is disabled or inaccessible. It inspects stored Stalwart settings, not SMTP connectivity, actual delivery, secret file access, or active configuration after a pending reload. The DKIM result requires both Stalwart and SES records to have been checked; it does not prove signatures or alignment. A successful test submission means queued, not delivered.

Backup marker status is unavailable by default: the observer keeps its observations in logs and the API container has no marker mount. To expose marker freshness, mount the observer's `OBSERVE_BACKUP_DIR` read-only into the API container, readable by its unprivileged user, and set `SETUP_BACKUP_MARKER` to the absolute path of its `last-success` file inside that container. The freshness threshold is 26 hours, the observer's default. Missing or unreadable markers are unavailable, future or stale markers need attention. This is not a restore verification; keep the observer and independent monitoring in place.

User creation requires a managed domain for the address, since the wizard registers it there, and an initial password of at least 12 characters. A domain listed only in `MAIL_DOMAINS` has no domain record: create its accounts with the sign-up API or the bootstrap command. The wizard registers each new user’s primary address with the domain service. Use the domain step to register the bootstrap administrator’s primary address too; the ingestion worker also needs a matching destination credential as described in the domain guide. Deliver it securely. A failed creation may leave a user or remote mailbox partially provisioned; inspect and reconcile before retrying. Public sign-up remains restricted. The current runtime does not deliver invitations.
